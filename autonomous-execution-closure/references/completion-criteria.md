# 状态与完成标准

## 状态语义

| 状态 | 使用条件 |
| --- | --- |
| NOT_STARTED | 尚未开始实际工作 |
| IN_PROGRESS | 正在推进已授权任务，含可继续的长任务 |
| TESTING | 正在验证修改或执行最终验收 |
| REPAIRING | 正在诊断、修复或重验失败步骤 |
| BLOCKED | 必需外部条件缺失，已确认无可行的已授权路径 |
| FAILED | 执行或验收已明确失败，合理方案或授权预算耗尽，无法在当前范围交付 |
| PASSED | 全部关键验收条件通过，实际交付物可用 |

这些是本 Skill 的工作记录语义，不替代宿主工具状态协议。工具有额外转换条件时遵守该协议。BLOCKED 和 FAILED 均不代表成功；条件变化并获授权继续后可恢复执行。用户暂停或取消时保留当前状态并明确暂停或取消，不强行归为失败。

## PASSED 门槛

逐项核对，全部满足才能宣布整体完成：

1. 用户要求的交付物已经实际生成，位置或访问方式可用。
2. 必要行为通过实际执行得到验证；纯分析任务则以用户要求的分析产物验收。
3. 必要目标测试、相关回归与最终验收通过。
4. 已知关键错误解决，关键未知项已消除。
5. 所有要求阶段完成；未经用户同意没有缩减范围或降低标准。
6. 最终结果满足原始要求及用户后续确认的有效修订。

构建通过、单测通过、部分数据通过、部署成功、任务启动、修复报告完成，都只能证明对应子项；不能自动将父任务标记 PASSED。未完成项即便已披露，若属于关键验收，仍不能判定整体通过。

## 交付格式

优先简短提供：

- 实际结果与交付位置。
- 验证方式、覆盖范围及结果，必要时链接证据。
- 影响使用的限制和未通过项。

未完成时明确当前状态，不使用“基本完成”掩盖关键失败。BLOCKED 报告必须包含具体失败步骤、实际尝试、已验证成果、客观限制和恢复所需的最小输入；FAILED 报告说明失败证据及已用尽的合理路径或预算。

## 行为自检案例

- 用户说“先分析，不修改”：完成分析后等待后续授权，不运行修复。
- 编译通过但实际入口报错：进入 REPAIRING，修复运行链路后重新验证，继续原任务。
- 阶段一通过但阶段二未启动：检查自动衔接与状态传递，不能以阶段一报告结束。
- 仅界面计数被改正而后端逻辑未修：不算缺陷修复，继续验证真实行为。
- 本地单测通过但集成仍失败：保留局部通过记录，整体不能 PASSED。
- 后端不可用且替代路径被禁止：尝试合理恢复，确认无法继续后报告具体 BLOCKED，不静默降级。
- 长任务已启动且仍有进展：继续观察到请求的终态；用户要求仅启动任务时，按该较小范围验收。
- 用户要求停止或预算到期：保存状态并停止相关工作，不擅自续期。
