# 错误诊断与修复协议

## 每次失败的闭环

1. 保存失败证据：操作或命令、退出状态、输入、实际输出、相关日志、版本及环境差异。仅保留必要信息，避免泄露凭据或无关数据。
2. 复现失败；若复现成本高、有破坏风险或依赖不可重放的外部状态，采用已有日志、最小样例或受控探测检验问题，明确证据限制。
3. 定位最早发生偏离的步骤。区分根因、后续症状、显示问题和过期状态。
4. 提出可证伪的根因假设，说明什么观察会支持或否定它；先做低成本且有区分力的检查。
5. 实施满足原要求的最小修复，保留用户改动、必要功能、输入约束和指定执行路径。
6. 重跑原失败步骤，验证原症状确实消失，且结果不是因跳过处理、返回默认值或使用旧缓存而产生。
7. 执行受影响的回归和阶段衔接检查，再恢复用户原始任务。

不得停在“原因已找到”“建议这样改”或“代码已修改”。未经实际验证，只能说已修改、待验证。

## 反复失败时改变策略

维护精简尝试记录：假设、动作、结果、排除或保留的原因。相同动作在相同条件下失败且无新证据时不继续盲重试。

根据证据改用合适策略：

- 缩小输入或执行范围，找到最小失败条件。
- 对照最后已知可用版本，检查配置、接口与运行产物差异。
- 增加必要观测，区分算法、环境、数据、调度和资源问题。
- 验证兼容的实现、工具或依赖版本；替代方案必须保留原始验收要求。
- 对瞬时外部故障使用有界重试；涉及写入时先确认原操作结果与幂等性。

不要机械规定所有问题重试相同次数。按风险、成本和用户预算设置合理尝试边界；每次继续都应能获得新证据或验证新方案。

## 环境问题

先核查入口、解释器、依赖、路径、配置、权限和实际后端。授权范围内优先采用项目已有环境或隔离修复，避免无关全局改动。不能仅凭一次启动失败就判定整个环境不可用。

替代后端被用户或项目规范禁止时，不使用该后端降级；如必需后端确实无法恢复，报告具体阻塞。不得模拟真实执行成功、伪造日志、吞掉关键异常、删除功能或修改测试预期来获得通过。

## 暂停条件

满足下列任一真实条件且无可行的已授权路径时，停止依赖该条件的操作：

- 必需权限、资源、输入、认证或关键决策不可获得。
- 所有合理且风险适当的诊断路径已失败，剩余动作超出授权或预算。
- 继续会违反约束或无法保证数据安全。

继续可独立完成的工作，并交代已执行操作、证据、尝试结果、未通过验收项、客观限制和用户最小必要动作。“环境问题”“后续再处理”不构成充分的阻塞说明。
