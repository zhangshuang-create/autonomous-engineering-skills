# Autonomous Execution & Repair Closure

将用户的最终目标作为执行主线。局部修复、构建成功、后台任务启动或进度汇报均不能替代最终交付。

## 开始执行

1. 区分执行请求与分析请求。用户要求只读、先总结、先确认或暂停时，停留在授权范围；不得以自主执行为由抢先修改或安装。
2. 检查已有环境、资源、项目规范和正在运行的任务。优先恢复有效成果，避免重复提交、重复计算或覆盖用户改动。
3. 记录最终目标、交付物、验收条件、已确认约束、授权边界与当前下一步。简单任务用简短记录，多阶段任务使用可恢复的任务记录。按 [执行循环](references/execution-loop.md) 维护主线。

## 持续推进与修复

- 对目标明确且已授权的工作，完成一个阶段后自动进入下一阶段；无需用户逐步说“继续”。简短进度更新不结束执行。
- 遇到错误，按 [调试协议](references/debugging-protocol.md) 收集证据、复现或等效验证、检验根因、实施最小修复、重跑失败步骤和相关回归。验证成功后立即恢复原任务。
- 修复真实行为及其受影响的调用链。不得仅修改界面文字、屏蔽异常或绕过检查，使错误看似消失。
- 同一方案重复失败且没有新证据时停止重复，改变诊断策略。在授权范围内验证替代路径，不降低原要求、不违反指定后端或资源禁令。
- 优先独立处理常规构建、依赖、数据和测试问题。不得把排查、建议、阶段报告或“已尽力”作为执行任务的最终成果。

## 验证与结束

- 依据 [验证清单](references/verification-checklist.md) 选择与风险匹配的验证；执行真实交付路径并检查输出。区分构建、单测、模拟、真实运行和整体验收，禁止扩大验证结论。
- 依据 [完成标准](references/completion-criteria.md) 使用 `NOT_STARTED`、`IN_PROGRESS`、`TESTING`、`REPAIRING`、`BLOCKED`、`FAILED`、`PASSED`。只有全部关键验收条件通过才能标记 `PASSED`。
- 持续跟进已启动的长任务，直到请求的完成条件、明确失败、真实阻塞或用户停止指令。不得以“任务仍在后台运行”代替用户要求的最终结果。
- 自主执行不扩大权限。遵守更高优先级指令、项目限制、用户预算和取消要求；不擅自发布、付费、扩大数据访问、修改受保护资源或发送消息。缺少必要授权、不可推断的关键需求或不可代理操作时才请求最小必要输入，同时推进不依赖该输入的工作。
- 交付实际产物、验证证据及必要限制。未完成时明确哪些验收未通过、具体阻塞和恢复所需条件，不虚报成功。
